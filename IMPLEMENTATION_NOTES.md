# Connector implementation checklist

The desktop shell has experimental read-only Hub navigation, but the safety model does not implement live relisting. A real connector must be implemented and verified before enabling any listing change. The following observations are a guide, not a stable API or an exhaustive mapping:

- Manage Listings filters can hide results. Confirm transaction type, status, office and agent filters before declaring an RXCU absent; exact-match and identity-check a single listing.
- Edit and archive open new tabs. Track browser window handles, verify the page and return to the correct listing.
- Capture every relevant editor tab, nested dialog, party, document, note, agent and portal selection. Preserve media order, captions, cover, floorplans and all descriptions. Verify downloaded photo-pack files, not only links or thumbnails. If access or capture is incomplete, stop before portal removal.
- Sale and rental both have address verification. Suburb is an autocomplete selection, not merely typed text. Operator must approve corrections before any removal or archive.
- Portal statuses initially load asynchronously. Verify each originally selected portal has actually been removed; do not infer removal from clicking a control.
- Archive uses cancellation and the mandate-expired reason. Confirm the identity and resulting status.
- Save creation particulars before later tabs. Preserve sale/rental differences and mandatory dates; do not invent mandate data. Capture the new ID as soon as it exists. Upload and compare all details and media before submission. Publication can remain pending after submission.
- Never retry a possibly executed archive, create or publish operation without reconciling the current Hub state. Retain local source data securely when manual recovery is needed. This system cannot promise rollback after archiving.

Unverified selectors, completeness rules and actual portal outcomes must fail closed. These observations contain no real listing data.

The copied-field inventory validates capture integrity, expected local-job reference, per-page guards and observation ordering before mapping the latest page observations. It preserves original field objects and paths, distinguishes missing/ambiguous/unresolved controls, and retains unmapped controls and related dialog records. It does not infer required fields or sale/rental branches, normalize prices/dates, invent selected suburb IDs, or turn historical observations into a verified backup.

Replacement comparison requires two explicitly selected, distinct RXCU references and numeric listing identities. The UI pins the original saved record, rechecks both local records and job identities before comparison, and clears stale results when selections change. It reads only local storage and does not call the Engine or browser. Exact observed values and raw selection/checkbox states are compared without normalizing them. Supported room controls remain scoped by category and position, with guarded parent-field bindings. Unknown controls, pending room observations, missing known controls, capture interruptions and historical chronology remain visible. Flat dialog observations duplicated in grouped reads are retained separately without inventing a room identity. All completeness, fidelity and publication-readiness flags remain false, even when observed fields match.

Observed existing room dialogs use caption spans such as Set bedrooms options, not native buttons. Room inputs repeat names and IDs across groups. Each group must stay scoped to its direct DIV under the visible MuiDialogContent-root, with its own numbered H6 heading, checkbox states and description. Hidden measuring textareas must be excluded. Bedroom, bathroom, kitchen, parking and lounge dialog schemas were inspected without changing fields; Escape closes them asynchronously. Zero-count captions may still look enabled and produce no dialog. Add option, Done and remove controls are not read-only capture actions.

Live connector qualification must also demonstrate an atomic server-side expected-revision precondition for each destructive operation. A read followed by a click is not an atomic concurrency safeguard. Hub support for this is unknown; do not set the connector ready or enable live writes until the requirement is met and independently verified. Required address values and suburb selection must be validated against the actual Hub form, not inferred from a partial inspection.

The read-only editor opener checks a unique RXCU row, its controlled Select menu, the numeric editor URL and both visible reference headings. Account ownership, result completeness and capture fidelity remain unverified.

Current observed Hub navigation uses native button tabs, not anchor links. Matched capture recognizes only Listing particulars, Deal Particulars, Media and Portals, checks selected/enabled states, and observes the actual resulting route without constructing it. The download button has title-case textContent but uppercase rendered text. Business selection codes are read only for nine observed names with an adjacent visible MUI combo and matching aria-hidden native input; arbitrary hidden fields remain excluded. Media image IDs, global positions and data-full-src references are recorded. The Listing images/Floor plan images headings label upload widgets, not separate image grids, so they cannot classify the displayed cards.

Optional download-event attribution requires a matching selected target/frame/reference filename and one completed GUID, plus stable ZIP bytes. Only the app-created dedicated default browser uses default-context download routing; externally supplied sessions require their explicit context. The auto-import compares the actual archive hash/size against the completion-bound byte receipt before recording any source association. Any event ambiguity, file change or cleanup uncertainty keeps the file unassigned. Event evidence does not prove exact click causality, account ownership, original resolution or source completeness.

Local download recovery shares a process lock with requests, checks the reviewed inventory again before clearing the pause, preserves the original intention in a protected receipt directory and leaves every file in place. It requires successful closure of the controlled browser plus operator confirmation that older/orphaned Quick Relist browsers are closed. It cannot independently verify another process's browser state or guarantee against malicious same-user file changes. Invalid or linked records keep the pause. Windows path/handle timestamps are compared within their own API to avoid inconsistent ctime semantics; UI action widths are recalculated after native font/layout initialization.

Real Windows synthetic tests and native ACL/locking checks are part of development qualification. Successful synthetic tests do not replace live Hub capture, download and sale/rental end-to-end validation.

The mutation boundary now carries a deeply immutable, fingerprinted request into each provider write and reconciliation. It binds exact account/source identities, expected source and replacement revisions, original capture, address approval, portal choices and archive settings. Replacement validation must be qualified and strictly non-mutating before removal, archive or creation. Source mandate values are preserved exactly; missing validity or a required date decision blocks the write. Receipts must match the exact command, and post-write revisions must agree with those receipts. Legacy unbound requests cannot be replayed. The default app still has no live provider. See [the mutation adapter contract](MUTATION_ADAPTER_CONTRACT.md) for the evidence and behavior required of a future provider.

The observed Portal table is not rectangular: ordinary detail rows have eight cells, the expiry row has five, the global publication row has one, and the action row has eight. There are no spanning-cell attributes explaining those differences. The single “Is published?” chip has no portal association and no action buttons in its cell. It is not independent evidence of external publication or removal. Table observations must retain actual row/cell membership rather than invent grid coordinates. Per-portal status semantics remain unqualified.

The five observed mandate/listing dates are MUI segmented pickers. Each allowlisted named aria-hidden input is bound through a unique input ID, its local label and a visible picker group to Year, Month and Day spinbuttons. Generated IDs are relational anchors, not selectors to hardcode. Missing native required/min/max/pattern attributes do not establish absent business validation; some labels carry asterisks. Do not read arbitrary hidden fields or infer a new mandate date from these observations. The “Bank mandate” label was observed pointing to the mandate-type input, so label association alone cannot establish a separate bank-mandate field.

The separate `hub_form_writer.py` component now contains concrete WebDriver field handlers and a synthetic-only execution factory. The public entry point is blocked and the component is not registered with the mutation engine. Its complete supported-form baseline includes unrequested controls; unknown controls, changed options, dependent-field resets, wrong identities and uncertain interactions stop the transfer. Source text and raw checkbox/date values are preserved rather than interpreted. Only the property-type open menu structure has been observed on Hub; other menus, keyboard behavior and persistence remain unqualified. No Save-labelled control was found in the inspected existing-editor states, which does not establish that field events are harmless or that the service lacks autosave. See `tests/HUB_FORM_WRITER.md` before extending this component.

`creation.py` adds a separate durable staged coordinator, and `creation_engine.py` adds optional partial-creation reconciliation and explicit resume APIs. Existing `core.py`, `mutations.py`, the desktop UI and launcher remain unchanged. A partial draft keeps the outer create operation uncertain; it cannot unlock ordinary Advance or become a new allocation. Resume binds the fresh authoritative checkpoint and original request, records the intention before dispatch, and requires provider-side checkpoint/revision comparison. The synthetic provider models these guarantees; it does not prove Hub supports them. See `CREATION_RECOVERY.md`, including the conservative identity-reuse limitation and missing live qualification.

`transfer_plan.py` maps two independently pinned saved captures through the source inventory into exact historical field candidates and target baselines. Source readability is separate from target editability; unresolved semantics and missing coverage remain blockers, and no executable request is produced. `hub_media_writer.py` exercises ordinary file-input selection against a nonce-bound localhost fixture whose server hashes received bodies. It checks selected File metadata before reading bytes, compares typed receipts exactly and never retries a send. The two observed upload widgets feed one shared grid, so separate photo/floorplan selection does not establish global order or metadata fidelity. This media-only component has no durable restart recovery or creation-coordinator integration; the future live upload strategy still needs qualification. Existing app and live gates are unchanged.

Passive inspection of the existing Hub media page also found that each card's whole wrapper is a focusable `div[role="button"][aria-roledescription="sortable"]`, with `aria-describedby` pointing to a dynamic drag-instructions node. Its instructions specify Space to pick up, arrow keys to move, Space to drop and Escape to cancel. This establishes an advertised keyboard interaction, not tested movement, saved order or atomic persistence. No separate drag handle was observed. The cards exposed an Add caption button but no caption text nodes or input values in the inspected state; this is not proof that stored captions are empty. No cover marker or cover control was observed. Do not infer cover from first position, and do not hardcode the generated description ID.

`media_metadata.py` and `hub_media_metadata_writer.py` add a separate synthetic-only metadata workflow with private append-only storage, deterministic per-stage commands, revision chains and native browser interactions. Uploaded-asset receipts bind byte identity, but do not prove the separately supplied metadata-stage baseline or revision transition. The fixture explicitly models zero-or-one cover, caption saves and a shared keyboard-sortable grid; these are not qualified Hub rules. Uncertainty requires separate read-only reconciliation, and a terminal rejection does not trigger a retry. A missing local journal, changed server epoch or contradictory receipt history cannot restart a progressed workflow. The modeled service ledger survives browser restarts only, not loss of the service. Unknown media metadata, rotation and tags block this partial handler rather than being discarded. Existing application, creation and upload components remain unchanged and are not automatically composed by this slice.

Windows Chrome qualification found that implicit incognito download routing canceled the same synthetic HTTP attachment that completed in a dedicated regular profile. The app therefore creates a new owner-only disposable regular Chrome profile, disables credential/password saving, and never reuses a user's existing profile. It removes only its recorded profile directory after a successful browser quit; failed startup, close or cleanup retains protected session files rather than risking removal while Chrome may still be using them. Crash recovery and secure erasure are not guaranteed.
